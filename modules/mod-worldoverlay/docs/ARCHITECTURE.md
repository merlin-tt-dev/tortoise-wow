# WorldOverlay architecture

## 1. Purpose

WorldOverlay provides named server-side world layers on existing instanced maps without requiring a client map patch.

The client continues to load the original map geometry. The server associates a stable overlay key with a dedicated runtime instance and loads module-owned content into that instance.

The design deliberately separates four identities:

```text
client map geometry
map id
runtime instance id
logical overlay key
```

Only the logical overlay key is persistent module content.

## 2. Tortoise facts this design builds on

The current Tortoise map manager already distinguishes maps by `(mapId, instanceId)` and exposes lookup by both values.

Normal dungeon instance creation is bind-driven: an existing player/group persistent state is preferred, otherwise the core generates a new runtime instance id.

`Player::SwitchInstance(uint32)` exists for switching to another instance of the same map, but its existing usage is not a complete cross-instance teleport API because destination coordinates and dungeon lifecycle/binding semantics still need to be handled correctly.

`MapManager::CreateTestMap()` can create an instanced map with a generated id, but it is explicitly a test/debug API and must not be adopted as the production lifecycle path without review.

Therefore the implementation must first verify whether the module can create and enter a named dungeon instance entirely through existing public APIs. If not, the preferred fallback is one narrow, generic core adapter rather than WorldOverlay-specific policy in the core.

## 3. Non-goals

WorldOverlay must not:

- replace the normal Tortoise dungeon/raid instance system;
- change ordinary portal or AreaTrigger behavior;
- repurpose random native spells to select an instance;
- persist a runtime instance id as the identity of an overlay;
- store overlay-only builders' objects in base `creature` or `gameobject` rows;
- require a client patch merely to create a separate server-side world layer.

## 4. Named overlay lifecycle

A definition such as:

```text
overlay_key = tele_city
map_id      = 36
```

is loaded at server startup into `WorldOverlayManager`.

The intended lifecycle is:

1. Load overlay metadata from `worldoverlay_overlay`.
2. Keep the overlay logical-only until first use unless configured for eager creation.
3. On first entry, allocate or resolve a runtime instance for the map.
4. Associate `overlay_key -> (map_id, runtime_instance_id)` in memory.
5. Create/load the map through a production-safe map-manager path.
6. Load overlay-owned creature and gameobject spawns into that map only.
7. Teleport the player to a destination that resolves to the named overlay.
8. On unload or restart, discard the runtime id. The overlay key and module-owned content remain persistent.

### Runtime id rule

The runtime id must be generated by the core's instance-id allocator or another collision-safe core API. World DB content must never assume that an old runtime id remains valid after restart.

## 5. Base spawn policy

Two logical modes are planned:

### INHERIT

The named instance receives normal map spawns plus overlay-owned spawns.

This is the phase-1 target because it preserves the existing map-loading model and is suitable for Tele City, whose construction is in a separate area of map 36.

### NONE

The named instance uses the same client geometry but suppresses ordinary base-world spawns and loads only overlay-owned content.

This enables a true reusable map template, but it must not be implemented by deleting or mutating base spawn rows. It requires a verified instance-specific spawn-loading filter/hook and is deferred until that hook is designed.

## 6. Overlay-owned spawns

Overlay builder data is stored separately:

```text
worldoverlay_gameobject
worldoverlay_creature
```

A row is addressed by `overlay_key` plus a module-owned spawn id.

The module-owned spawn id is a database identity only. Runtime creature/gameobject GUID allocation must use the core's supported object/GUID allocation path; table primary keys must not be blindly reused as live ObjectGuids.

Objects are materialized only into the runtime map associated with the matching overlay key.

This gives the required isolation:

```text
map 36 / normal instance A : no Tele City overlay spawns
map 36 / normal instance B : no Tele City overlay spawns
map 36 / tele_city         : Tele City overlay spawns present
map 36 / bot_lab           : only bot_lab overlay spawns present
```

## 7. Destinations and teleport resolution

A destination has a stable key and one of three phase-1 instance policies:

```text
AUTO     - use normal Tortoise map/instance resolution
CURRENT  - keep the current instance when already on the destination map
OVERLAY  - resolve a named WorldOverlay instance
```

`OVERLAY` is the important WorldOverlay path.

Example:

```text
destination_key = tele_city_moonwell
map_id          = 36
overlay_key      = tele_city
instance_policy  = OVERLAY
x/y/z/o          = Moonwell coordinates
```

The manager resolves the logical overlay to its current runtime instance, then performs an instance-aware teleport.

A production-safe `TeleportToInstance(player, mapId, instanceId, x, y, z, o)` behavior is an implementation requirement. It must not be simulated by changing persistent player/group dungeon binds just to reach an overlay.

## 8. Teleport bindings

`worldoverlay_teleport_binding` provides a generic mapping from a source entry to a destination key.

Initial source types are intentionally small:

```text
1 = ITEM
2 = GAMEOBJECT
3 = CREATURE
```

This is sufficient for a Chronostone, overlay portal/orb, or NPC interaction while keeping destination logic centralized.

More complex gossip menus with multiple destinations should use a later menu/action table instead of overloading this simple one-to-one binding.

## 9. Builder safety

Builder commands use `.wo` with `.woverlay` as a long alias.

A builder operation that adds/moves/deletes overlay content must require an active overlay context. The command must display the active overlay before destructive operations where practical.

Safety properties:

- `.wo go add` writes only `worldoverlay_gameobject`.
- `.wo npc add` writes only `worldoverlay_creature`.
- `.wo go delete` must reject base-world gameobjects.
- `.wo npc delete` must reject base-world creatures.
- ordinary `.gobject add` / `.npc add` keep their original semantics and are not intercepted.

This makes it difficult to accidentally contaminate the original instance while building an overlay.

## 10. Standard instance compatibility

WorldOverlay must coexist with the original teleport path.

A normal Deadmines portal or AreaTrigger continues to enter a normal bind-selected Deadmines instance.

A WorldOverlay destination explicitly resolves `tele_city` and enters the dedicated named instance.

No normal AreaTrigger rows need to be changed for this feature.

## 11. Persistence and reset policy

Phase 1 distinguishes logical persistence from map-object lifetime.

`PERSISTENT` means the overlay definition and content persist indefinitely, while its runtime instance may be recreated after restart or unload.

Future policies may include:

```text
PERSISTENT
WHEN_EMPTY
MANUAL
SCHEDULED
```

Dungeon reset semantics must be audited before any overlay is allowed to inherit normal reset behavior. A named world must never disappear merely because a normal dungeon reset scheduler assumes it is an ordinary dungeon run.

## 12. Module boundaries

Preferred module layout:

```text
modules/mod-worldoverlay/
  README.md
  docs/
  data/sql/world/
  examples/
  src/                  # added with runtime implementation
```

Planned runtime components:

```text
WorldOverlayManager
WorldOverlaySpawnManager
WorldOverlayTeleportManager
WorldOverlayCommandScript
```

If a core change is required, it should expose only a generic map/instance operation. Overlay naming, DB schema, builder commands and policy stay inside the module.

## 13. First implementation spike

Before writing the full runtime:

1. Prove creation of a generated, dedicated runtime instance for map 36 without a normal player/group bind.
2. Prove an instance-aware teleport into that exact map copy.
3. Prove one module-owned GO can be spawned only in that copy.
4. Restart and prove the overlay resolves to a new runtime id while retaining the same logical content.
5. Enter Deadmines normally and verify the overlay GO is absent.

Only after these five checks should the builder surface expand.
